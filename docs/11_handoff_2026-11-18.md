## 1. 作業の進め方（このリポジトリの約束ごと）

- 作業ブランチ: セッションごとに指定されたブランチ（今回は `ccr-efc000b2-ma3pnw`）。1件ごとに `origin/main` から作り直して使う
  ```
  git fetch origin main && git checkout -B <作業ブランチ> origin/main
  git push --force-with-lease=<作業ブランチ>:<リモートの今のSHA> origin <作業ブランチ>
  ```
  - squash でマージしたあと、前の作業のコミットを残したまま次の作業を足すと、PR がコンフリクトになる（#775 で起きた）。
    必ず `origin/main` から作り直す。起きたら `git rebase --onto origin/main <マージ済みのコミット>` で外す
- 確認（コミット前に毎回）: `npx tsc --noEmit` → `npx eslint <変えたファイル>` → `npx vitest run` → `npm run build`
  - `npm run build` は Next.js 16.4.2 のセキュリティの知らせで1回目が止まることがある。もう一度実行すると通る（4章）
- 機能を足したら `src/lib/release-notes.ts` の `RELEASE_NOTES` の先頭に1件足す。**ただし一本化計画の試験中の機能（管理者だけ）は足さない**
- 利用者が「pr作成してマージ」と言ったら PR を作って squash でマージ（head の SHA は40桁で指定）。言われるまでは PR を作らない
- マイグレーションは利用者が Supabase の SQL Editor で手で適用する。SQL は回答の中に貼って渡す
- 利用者からもらったファイル（会社の情報が入った PDF・エクセルなど）はリポジトリにコミットしない。
  何も記入していない入管の公式の様式（提出書類一覧表・参考様式）は `public/forms/` に入れてよい（アプリが使うため）
- このセッションの環境では Supabase の service role key が使えない（伏せ字）。本番のデータを直接読む・書くことはできない。
  データが要るときは利用者に画面で操作してもらうか、SQL を流してもらう
- 「新規引き継ぎ作成」「新規ページへ引き継ぎ」と言われたら、`CLAUDE.md` の手順（docs の handoff ＋ Obsidian 用ノート）で進める
- 利用者は画面の見本の画像（「サンプル画像作成」）をよく求める。アプリの画面をまねた HTML を Playwright で撮って送っている
  （実際の画面ではないことを必ず書く）
